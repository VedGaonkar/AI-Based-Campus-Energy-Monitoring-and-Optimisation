# Institution workspaces

CE-013 supports independent institutions, each with one building. There is no multi-building portfolio or cross-institution dashboard. The existing Node/Express, MongoDB/Mongoose, React and worker stack remains in place.

## Accounts and onboarding

Email addresses remain globally unique. One account can have multiple explicitly authorised memberships, each with its own role and room scope. A display name is editable; the generated internal institution ID is immutable. Renaming never moves records or changes membership IDs.

New administrators register with an institution/building name, password and the server's `ADMIN_INVITE_KEY`. This creates a private, empty institution, including no sample rooms, floors, schedules, readings, devices or incidents. Start with **Admin management → Building setup**. **My profile → Your institution workspace** edits the name, allows public name suggestions, generates a private identity code and creates expiring membership invitations.

Login requires selecting the intended institution and verifying the account's active membership on the server. Type at least three characters and choose a suggestion, or expand **Private institution or invitation code**. Suggestions are debounced 300ms and return only ID/name, at most eight matches. `INSTITUTION_DISCOVERY_ENABLED=false` disables public suggestions globally; each institution can also remain private. Identity codes select a workspace but grant no membership. Keep codes private and regenerate them to revoke the old code.

Use an administrator-created invitation to join an existing workspace. A new account supplies it during registration. An existing account uses **Accept an institution invitation** with its current credentials on the login screen. Invitations are single-use, expire in 1–168 hours, optionally restrict email, and fix role/room scope. Knowing a workspace name or the shared enrollment key does not join another institution. Administrators can then maintain room permissions in Users & permissions. To change workspace, sign out and select another authorised institution; a valid password alone never chooses a workspace silently.

## Existing installation migration

Back up the configured MongoDB before applying. Stop all API/worker instances, including separately supervised instances, so old code cannot write unscoped records. Run from the repository root:

```bash
npm run stop
npm run migrate:institutions
npm run migrate:institutions -- --apply
npm run dev
```

The first migration command is a dry-run: review counts/conflicts before applying. This migration preserves the original operational database, record IDs, password hashes, roles, inactive accounts and existing relationships. It creates a legacy institution representing the whole original installation, copies global account identities, creates memberships and annotates operational records with the immutable institution ID. It does not assign ambiguous data to a chosen administrator. Foreign ownership, conflicting global identities and unknown non-empty collections block application and require an operator mapping/reconciliation. An interrupted migration leaves the institution inactive and can be rerun after resolving the cause. Startup fails closed until migration is complete.

Old sessions require fresh login and institution selection. Legacy room QR tokens still resolve exclusively to the legacy institution. Re-pair phone demos and reissue scoped camera/gateway credentials: new tokens/HMAC inputs include institution identity. Existing histories are retained. Pending work retains its due/expiry information and undergoes the existing current-state worker checks; expired work is not replayed. Do not restore pre-migration code against the migrated directory while accepting new registrations. Restore the complete backup in a separately controlled recovery procedure if rollback is needed.

The MongoDB service account needs access to the global directory and generated per-institution databases on the same MongoDB deployment. Provision appropriate credentials/backups for those databases before production use. Database names are generated by the backend, never accepted from browser input. No automatic database drop or account deletion exists in this milestone.

## Explicit dedicated demo

Normal startup never seeds data or resets accounts. To explicitly enable a local showcase:

```bash
npm run setup -- --enable-demo
npm run seed
```

Setup generates missing strong `DEMO_ADMIN_PASSWORD` and `DEMO_VIEWER_PASSWORD`, and dedicated `DEMO_ADMIN_EMAIL` / `DEMO_VIEWER_EMAIL`, only in ignored local `.env`. Read them there; do not publish them. Existing values, accounts and roles are preserved. `ENABLE_DEMO_SETUP=true` and `DEMO_MODE=true` are required. Production additionally requires explicit `ALLOW_PRODUCTION_DEMO_SEED=true` with operator-provisioned credentials; local credential generation is refused in production.

The seeder creates one dedicated, discoverable **Campus Energy Demo** institution, visibly simulated fixtures and an administrator/viewer membership. It stores password hashes, not plaintext passwords. Repeated seeds fill missing fixtures without resetting existing passwords, policies or roles. Conflicting/inactive identities or changed demo roles fail with an actionable error rather than silently repurposing/reactivating accounts. Changing an environment password after the account exists does not reset its hash; use an explicitly reviewed account-recovery process. Prior legacy sample accounts/data remain in their original institution and are not repurposed.

Environment edits take effect after restarting the backend/worker (`npm run stop`, then `npm run dev`); they do not reload running processes. Secrets never belong in Vite/public configuration.

## Isolation and limits

The global directory stores identities, memberships, institution metadata and hashed invitations/codes. Operational collections, credentials, room scopes, reports, caches and service instances are separate per institution. Trusted request context comes from authenticated membership or a validated institution-qualified public capability. Background workers iterate active institutions; sockets validate membership and qualify subscription rooms. Ingestion requires both institution identity and its source-specific credential. Assistant/exports use the same scoped services; no independent unscoped data tool is exposed.

This is application isolation on a shared MongoDB deployment, not separate database infrastructure or a production security audit. Directory/membership and per-database writes are resumable operations, not cross-database transactions. If onboarding fails mid-write, an operator must reconcile an inactive institution/orphan identity before retrying; do not delete or repurpose existing accounts to hide partial state. A claimed invitation whose membership write failed retains `usedBy` evidence for operator reconciliation. Back up both directory and operational databases together. Production retention, shared rate-limit storage and broader account recovery remain deployment work. Physical controls remain disabled/simulated.

## Verification commands

```bash
npm test
npm run build
node scripts/institutions-browser.mjs
npm run check
npm run check:client-secrets
```

The workspace tests use isolated databases, two institutions and overlapping local IDs; they cover reads/writes, invitations, private identity, rename, integration caches, source credentials, phone capabilities, jobs, sockets, migration and repeated demo seeding. Browser checks require installed Chrome/Edge (or `BROWSER_EXECUTABLE`) and a production build. They never use the configured user database. Live devices, production hosting and a real-phone network remain unverified.

New institution memberships retain their assigned role even when a non-admin supplies the shared enrollment key. An authorised workspace administrator must change an existing role. The original legacy institution retains its earlier password/key activation workflow for compatibility; this exception never creates another institution membership.

Registration setup clarification (CE-015): choose Create a new institution or Join an existing institution. POST /auth/register accepts optional registrationMode=create|join (legacy unambiguous requests remain compatible). Create requires institutionName + server adminKey and no invitationToken. Join requires an authorised invitationToken and no institutionName; admin invitations additionally require the server key. Mixed requests return400 REGISTRATION_MODE_CONFLICT without creating an account; invalid invitations remain403 and never fall back to creating a site. The form renders only the selected mode and clears inactive values. Signed-out /auth/me401 is expected; development StrictMode can issue the initial check twice. Browser-injected contentscript/ObjectMultiplex messages are separate from backend registration errors.
