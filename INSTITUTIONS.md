# Institution workspaces

CE-013 supports independent institutions, each with one building. There is no multi-building portfolio or cross-institution dashboard. The existing Node/Express, MongoDB/Mongoose, React and worker stack remains in place.

## Accounts and onboarding

Email remains globally unique. Account password hashes and existing immutable building memberships/local roles/room permissions are preserved. Institution display names are editable labels, not authorization keys.

Sign in with email/password only. One active membership opens automatically. Multiple active memberships produce a five-minute password-authenticated selection session with no operational access. The server returns only authorised building identities and rechecks active account, membership and local role on selection. Sessions and CSRF tokens rotate. Signed-in users may switch authorised memberships in My profile. No code is required for subsequent login.

Administrator registration requires full name, email, password/confirmation, building name, a chosen Set Building Join Code value and the configured Administrator registration key, and always creates a new empty building with a new immutable ID. Viewer registration omits building name and supplies the Building Join Code; the server resolves its building and fixes the role to Viewer. Submitted role/building IDs and obsolete invitation fields are rejected. Existing global emails cannot register again or be silently moved.

Admin management ? Building setup and My profile offer a write-only Building Join Code setting. Use 8-64 case-sensitive ASCII letters/numbers/optional hyphen/underscore, including letters, numbers and six distinct characters. The code is never returned. Replacement stops old-code admissions, disabling blocks new Viewer registration, and existing memberships retain access. Rename changes no IDs or code resolution. Existing buildings start with registration disabled until their administrator sets a code.

Discovery, private identity-code and membership-invitation endpoints are retired with 410 responses. Historical admission records remain stored for audit and cannot grant new memberships. Authenticated administrator user/role management retains its separate permissions.

## Existing installation migration

Back up the configured MongoDB before applying. Stop all API/worker instances, including separately supervised instances, so old code cannot write unscoped records. Run from the repository root:

```bash
npm run stop
npm run migrate:institutions
npm run migrate:institutions -- --apply
npm run dev
```

The first migration command is a dry-run: review counts/conflicts before applying. This migration preserves the original operational database, record IDs, password hashes, roles, inactive accounts and existing relationships. It creates a legacy institution representing the whole original installation, copies global account identities, creates memberships and annotates operational records with the immutable institution ID. It does not assign ambiguous data to a chosen administrator. Foreign ownership, conflicting global identities and unknown non-empty collections block application and require an operator mapping/reconciliation. An interrupted migration leaves the institution inactive and can be rerun after resolving the cause. Startup fails closed until migration is complete.

Old pre-migration sessions require fresh password login; selection is only needed for multiple memberships. Legacy room QR tokens still resolve exclusively to the legacy institution. Re-pair phone demos and reissue scoped camera/gateway credentials: new tokens/HMAC inputs include institution identity. Existing histories are retained. Pending work retains its due/expiry information and undergoes the existing current-state worker checks; expired work is not replayed. Do not restore pre-migration code against the migrated directory while accepting new registrations. Restore the complete backup in a separately controlled recovery procedure if rollback is needed.

The MongoDB service account needs access to the global directory and generated per-institution databases on the same MongoDB deployment. Provision appropriate credentials/backups for those databases before production use. Database names are generated by the backend, never accepted from browser input. No automatic database drop or account deletion exists in this milestone.

## Explicit dedicated demo

Normal startup never seeds data or resets accounts. To explicitly enable a local showcase:

```bash
npm run setup -- --enable-demo
npm run seed
```

Setup generates missing strong `DEMO_ADMIN_PASSWORD` and `DEMO_VIEWER_PASSWORD`, and dedicated `DEMO_ADMIN_EMAIL` / `DEMO_VIEWER_EMAIL`, only in ignored local `.env`. Read them there; do not publish them. Existing values, accounts and roles are preserved. `ENABLE_DEMO_SETUP=true` and `DEMO_MODE=true` are required. Production additionally requires explicit `ALLOW_PRODUCTION_DEMO_SEED=true` with operator-provisioned credentials; local credential generation is refused in production.

The seeder creates one dedicated **Campus Energy Demo** institution, visibly simulated fixtures and an administrator/viewer membership. It stores password hashes, not plaintext passwords. Repeated seeds fill missing fixtures without resetting existing passwords, policies or roles. Conflicting/inactive identities or changed demo roles fail with an actionable error rather than silently repurposing/reactivating accounts. Changing an environment password after the account exists does not reset its hash; use an explicitly reviewed account-recovery process. Prior legacy sample accounts/data remain in their original institution and are not repurposed.

Environment edits take effect after restarting the backend/worker (`npm run stop`, then `npm run dev`); they do not reload running processes. Secrets never belong in Vite/public configuration.

## Isolation and limits

The global directory stores identities, memberships, institution metadata, secure join-code verifiers/lookups and retired historical admission records. Operational collections, credentials, room scopes, reports, caches and service instances are separate per institution. Trusted request context comes from authenticated membership or a validated institution-qualified public capability. Background workers iterate active institutions; sockets validate membership and qualify subscription rooms. Ingestion requires both institution identity and its source-specific credential. Assistant/exports use the same scoped services; no independent unscoped data tool is exposed.

This remains application isolation on shared MongoDB, not separate infrastructure or a production security audit. Directory and operational writes span databases without a transaction. Codes are validated before identity writes; provisioning accounts stay inactive until membership persistence succeeds. Caught failures compensate only documents created by that request. A process crash can leave inactive provisioning metadata requiring operator reconciliation; never move/delete/reset existing users to conceal a partial operation. Back up both directory and operational databases.

Codes use a salted bcrypt verifier and purpose-separated HMAC-SHA256 lookup with the existing server session secret. A partial unique index maps each active lookup to one building. Keep SESSION_SECRET stable: rotating it preserves account/password membership access but requires administrators to replace code lookups. No plaintext code, global default or retrieval endpoint exists.

Registration and replacement/disabling use a persisted per-building mutex on standalone MongoDB. There is no automatic lock stealing that could admit a paused writer under a revoked code. A crashed holder fails closed for new admissions/code changes; existing member login is unaffected. To recover, stop every API writer, reconcile inactive provisioning identities, inspect joinLockOwner/joinLockAt and audit evidence, then clear only the verified orphan lock before restarting. Never clear a running writer's lock. Production shared throttling and automated provisioning/recovery remain deployment work.

## Verification commands

```bash
npm test
npm run build
node scripts/institutions-browser.mjs
npm run check
npm run check:client-secrets
```

The isolated API suites cover empty Administrator onboarding, Viewer codes, invalid/disabled codes, unique lookup races, rotation serialization, rename, rollback, rate limits, secret-free responses/audits, password/hash/member preservation and authorised multi-membership choice. Existing cross-building API/job/socket/source/migration/demo regressions remain. Build first, then run `npm run test:auth-browser` for both forms, password-only login, write-only rotation, linked building labels, authorised choice and 390px layout. These checks do not use configured user data. Live devices, real-phone networking and production recovery remain separate acceptance work.
